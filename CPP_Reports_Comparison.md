# Comparison: `CPP_Language_Constructs.md` vs `CPP_DIALECT.md`

## What They Are

|  | `CPP_Language_Constructs.md` (mine) | `CPP_DIALECT.md` (uploaded) |
|---|---|---|
| Project | CPPBankProject (banking domain demo) | toad-x11 (X11 GUI library) |
| Purpose | Inventory of constructs used by the codebase | Audit of the dialect targeted + portability verdict |
| Tone | Catalog / reference | Forensic audit, with verdict + evidence + recommendations |
| Sections | 14 + summary | 7 numbered sections (verdict, evidence, features, GNU extensions, custom replacements, summary, modernization) |

## Standard Targeted

Both reports land on the same era — **C++03** — but for different reasons:

- **Mine** states C++03 as a deliberate choice (the code explicitly avoids C++11+ features for a Java-modernization study).
- **Uploaded** states C++98/03 because the project is genuinely old (autoconf 2.61, copyrights 1995–2005) and predates standardization of `shared_ptr`, `nullptr`, lambdas.

## Build Configuration

- Mine doesn't analyze build flags (the project is small and self-contained).
- The audit dives into `CXXFLAGS`: no `-std=...`, `-frtti`, `-Wno-pmf-conversions`, plus the `# DEFINES += -DOLDLIBSTD` legacy hint. This is an audit-grade detail my report doesn't need.

## Standard Library Headers

Both list the C++03-era headers. The audit has a usage-count table (e.g. `<vector>` 15, `<map>` 17, `<iostream>` 27) and explicitly enumerates what's *absent* (`<memory>`, `<functional>`, `<unordered_map>`, `<chrono>`, `<thread>`, `<regex>`, `<filesystem>`). My report only lists what *is* used.

## Language Features — Overlap

Both projects use: templates (audit: ~40 declarations; mine: none — my report doesn't list templates because the bank project doesn't define any), virtual functions / pure virtuals, multiple inheritance (audit) vs. multi-level single inheritance (mine), RTTI / `dynamic_cast`, exception handling, operator overloading (audit) vs. none (mine), `friend` declarations, `typedef` aliases, `static_cast`/`dynamic_cast`, raw pointers, manual `new`/`delete`.

## Language Features — Divergences

| Feature | Bank project | toad-x11 |
|---|---|---|
| Templates | None defined | ~40 template declarations (`GSmartPointer<T>`, `GModel<T>`, signal classes) |
| Multiple inheritance | Not used (single + multi-level) | Common (`TBitmap : public TOADBase, public TSmartObject`) |
| Operator overloading | Not used | `operator[]`, `operator=`, `operator->`, conversion operator `T*()` |
| `explicit` constructors | Not used | 2 occurrences |
| Bitfields | Not used | 62 occurrences (`bool lock:1;`) |
| Pointer-to-member functions | Not used | Central — drives the signal/slot system |
| `mutable` | Not used | Not used |
| Function pointers | Used as a strategy hook | Used heavily, dispatched via PMF casts |
| `friend` count | ~12 specific functions named | ~37 occurrences |
| Custom containers | None — uses STL directly | Bundles its own `stl/vector.hh`, `stl/deque.hh` |
| Smart pointers | None (raw `Account*` + manual delete) | `GSmartPointer<T>` + intrusive `TSmartObject` |
| Signals/slots | None | `TSignal` + `CONNECT` macros, generated by a Perl script |
| Macros | Object-like constants only | Used as a language: `CONNECT`, `TCLOSURE2`, generated variadic family |

## GNU / Non-Portable Extensions

This is a major asymmetry.

- **My file**: zero — the bank project is portable C++03.
- **The audit**: a whole section listing `typeof()`, GCC variadic-macro `ARGS...` with `, ## ARGS`, `__attribute__((aligned(16)))`, the pre-ISO `<ostream.h>` header on `__WIN32__`, and an external Perl preprocessor that emits `connect.hh`. The audit also flags the `throw()` empty exception specs that are deprecated in C++11 and removed in C++17.

## Custom STL Replacements

- **Mine**: none — the bank project relies entirely on `std::vector`, `std::map`, `std::string`, `std::ostringstream`, etc.
- **The audit**: documents `GSmartPointer` (pre-`shared_ptr`), `TSignal` (pre-`std::function`/lambda), bundled `stl/vector.hh` / `stl/deque.hh`, and `TException : std::exception` with `throw()` specs.

## Modernization Advice

- **Mine**: none — the inventory is descriptive only.
- **The audit**: a numbered "what to do if resurrected" list — bump to `-std=gnu++17`, replace `throw()` with `noexcept`, swap `typeof` for `decltype`, swap GCC variadic syntax for `__VA_ARGS__` (or variadic templates), retire `GSmartPointer` for `std::shared_ptr`, retire `TSignal/CONNECT` for `std::function`+lambdas, delete the `<ostream.h>` branch.

## Summary

The audit is the more rigorous of the two — it states a verdict, backs it with evidence (header counts, line numbers, GNU extensions), and ends with a portability action plan. My file is a flat catalog of constructs without verdict, build-flag analysis, "what's absent" reasoning, GNU-extension call-outs, or modernization guidance.

If `CPP_Language_Constructs.md` were lifted to the same grade, the additions would be:

1. A verdict paragraph.
2. A build-flag section.
3. An explicit "modern C++ features that are absent" list.
4. A modernization-notes section.
